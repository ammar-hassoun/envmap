{# One values file, as text, in a window over the list it was opened from. WHY A WINDOW AND NOT A PAGE There WAS a page — a two-column comparison of what git declares against what the cluster is running, with a structured editor per key. It was retired on request, and the reason it lost is the same reason the log and describe windows exist: you are looking at one file out of seventeen, and a navigation costs you the list, the environment you were in and your place in it. Every reason anybody actually opened that page was one of three things — read the file, change a value, push it — and all three fit in a window. WHY TEXT AND NOT A KEY-BY-KEY FORM The form was the clever half and the wrong shape. A values file is edited by somebody who knows YAML, and the things they want to do — move a block, add a list item, fix indentation, read a comment that explains why a value is pinned — are not "set key to value". The text is the artefact under version control, so the text is what gets edited, and the diff at the bottom is the same diff git will commit. THE THREE BUTTONS, IN THE ORDER THEY ARE SAFE `save` writes the WORKING COPY only. Nothing has left the machine, the row shows `edited`, and it can still be thrown away — that is why discard exists and why saving is not frightening. `seal` encrypts one value against this cluster's controller and writes the blob into the file. Also working-copy only. `commit & push` is the irreversible one, so it is last, it demands a message, and it reports the sha it verified on the remote. SEALING, AND WHY IT IS A KEY AND A VALUE RATHER THAN A SELECTION Sealing the highlighted text would be the obvious gesture and it would be a trap: a sealed blob is scoped `strict` to one namespace AND one secret name, so it only ever decrypts inside the block it was scoped for. Encrypting a selection wherever the caret happened to be would produce something that looks right, commits cleanly, and fails to decrypt in the cluster — the worst possible failure for a secret. So the panel names the scope it is sealing into, reads it off the file itself, and puts the blob where that scope is valid. Rotating an existing key is the same gesture with an existing name, which the panel offers as chips. The plaintext goes to the server and to kubeseal. It is never echoed back, never stored, and the audit line records the key's NAME only. #}
