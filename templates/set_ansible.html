What it may do
{# The one switch that matters. Off on a new installation, so an inventory can be built and playbooks written and dry-run before anything on this page can change a machine. #}
With this off, every run from this portal is a dry run: ansible reports what it would change and changes nothing. Turning it on does not grant it to anybody — a person also needs the Ansible: run playbooks area, and a group marked production still has to have its name typed. Every run is audited either way.
This is the same posture as a cluster's “allow management”: the portal being willing, and the credentials being allowed, are two separate things.
How many hosts ansible works on at once. Its own default is 5. Raising this makes a run across a large group faster and makes the load it puts on the portal, and on whatever the hosts talk to, proportionally larger.

How long ansible waits for a host to answer. This is what decides how long a playbook takes to fail against a machine that is simply switched off.
{# On by default: a terminal on a host is the one place a person acts on a machine free-hand, which is exactly what a bastion records. Off is a deliberate choice, and the empty Recordings tab says where the switch is. #}
When on, opening a terminal on an inventory host records the screen as a replayable cast and the commands as a transcript, both on the Recordings tab — the commands are also in the audit trail either way. The recording is output only: a value a host asks for without echoing back (a password) is never in it.

How a run reaches a host

Worth knowing before the first real run, because none of it is configurable here and all of it is visible:

  • The portal connects from wherever the portal runs — in a cluster, that is the pod's own network. A host it cannot reach on SSH is a host no playbook here can touch, however correct the playbook is.
  • Each group's key is encrypted at rest and written to a 0600 file inside a private directory that is removed when the run ends. A group can instead name a key path, for an installation that must not hold keys in its database.
  • The inventory, the playbook and any extra variables are files, and the command is built as a list of arguments. Nothing typed on these pages reaches a shell.
  • Every run keeps the whole output, the exact command, who started it and ansible's own recap. That is the record afterwards.
