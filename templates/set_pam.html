Privileged Access
Off on a new installation. Turning it on adds the target catalogue and session recording; it does not let anyone connect to anything on its own — that is the separate switch below, plus the Privileged Access and Privileged Access: connect areas on a person's roles. {% if not cfg.enabled %}

Live sessions
Off on a new installation: a catalogue can be built and reviewed before anything can be dialled. Turning it on grants nobody anything on its own — a person still needs the Privileged Access: connect area, and a production target still has its name typed. Every session is recorded and audited either way.
SSH sessions are recorded as a replayable cast plus a command transcript; RDP/VNC as a Guacamole recording. Each recording is checksummed when it is filed, so a later change to it is provable. The recording is output only — a value a host asks for without echoing (a password) is never in it.
Session governance a PAM constrains as well as records
When required, the operator must give a ticket URL, the session time, and a summary of the work before the session opens. All three are stored on the recording and written to the audit trail beside the connect.

Apache Guacamole's guacd renders RDP and VNC to the browser. It ships as a sidecar; until it is reachable, RDP/VNC targets say so and cannot be connected. SSH does not use it.
{#- SIZE THE BROWSER TO THE CLUSTER IT RUNS IN. These were fixed in code, so an install whose nodes cannot spare 768Mi and a pod slot had no way to make a seat fit — and the failure it got was the scheduler's, after the click, rather than a number it could change. Seen on a cluster running at 99% of memory requests on one node and at its pod cap on the other. -#}
What each browser pod asks the scheduler for. The REQUEST is what has to be free on a node before a seat can start at all; the LIMIT is what the browser may grow to while rendering. On a small or busy cluster a seat that cannot be placed fails with the scheduler's own words — lower the request to fit, knowing a browser given too little memory renders slowly or not at all.
Only used by the button above, when this portal adds the gateway to its own deployment. It matters for a mirrored or air-gapped install: the gateway is a sidecar, so an image the cluster cannot pull stops the whole pod rather than just the gateway. Point it at your own registry before pressing it.

A web application cannot be recorded on its own — guacd speaks RDP and VNC, not HTTP. So the portal starts a browser for the session, points it at the target and lets guacd render that. One pod per session, deleted when the session ends: two people sharing one browser would share its cookies. Off here, a web target is still catalogued and its open is still audited — it simply is not recorded.
The cluster and namespace the browser pod is created in. Management must be enabled for that cluster — a seat is a pod, and a pod is a write. The stream reaches guacd over a port-forward, so the browser does not have to run in the portal's own cluster; the honest cost is that it goes through that cluster's API server.
It must serve VNC and accept a URL over WebDriver — a Selenium standalone image does both. This product deliberately does not ship its own browser: that would be a second artefact to build, sign and re-patch for every browser CVE.
{#- LABEL BEFORE ITS INPUT, and each pair kept together. The labels used to TRAIL their boxes — "[1] VNC [1] WebDriver" — so the eye cannot tell whether a box is the thing named after it or before it. Asked directly: "where is the option to set it to 4444?", by somebody standing on this page with both boxes in front of them. A control nobody can find is a control that is not there. -#}
The image's own defaults — VNC 5900 and WebDriver 4444 for the Selenium image above. The VNC password is only ever used over the loopback inside this pod, never exposed.
Leave this blank for the shipped arrangement: guacd runs as a sidecar in this pod, so the browser is on its loopback and 127.0.0.1 is right. Fill it in only when guacd runs somewhere else — it would otherwise dial its own loopback and find nothing. Put an address that reaches this portal from guacd.
kept running · 0 creates one per click
A browser created on demand costs its image pull with somebody watching — measured at 36.9s cold against 4.3s warm on a real cluster. One warm browser makes the usual click about two seconds. It is claimed by exactly one session and deleted afterwards, never reused, so nothing is shared between people. The cost is one idle pod whenever recorded web sessions are on.
seconds
Only the FIRST run on a given node pays this — the image is cached afterwards. It was fixed at 120s, which turned a slow pull into a failure rather than a wait: a 1.5 GB image on a slow link was seen still pulling at 268 seconds.
seconds
Not a failure deadline. A single-page application with a live connection never reports that it finished loading, so the session is handed over on where the browser actually IS — asked directly, answered instantly — rather than on the page admitting it settled. Raise it only if an application needs longer before it is worth looking at.
seconds
The pod's own deadline, and the reason a lost session is not a browser left logged in for ever: it stops by itself even if the portal never gets to delete it. There is deliberately no unlimited option.
A seat whose session died with the portal has already stopped by its own deadline, but it still occupies a name in kubectl get pods. This clears those. It only ever removes pods this portal named.
