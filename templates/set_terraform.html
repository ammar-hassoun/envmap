What it may do
Off on a new installation: a stack can be written and planned — which changes nothing — before anything here can create or destroy a machine. Turning it on does not grant it to anybody — a person also needs the Terraform: apply area, and a stack marked production still has its name typed. Every run is recorded either way.
This is the same posture as Ansible's “real runs” and a cluster's “allow management”: the portal being willing, and the credential being allowed, are two separate things.
resources at once
How many resource operations Terraform runs concurrently. Its own default is 10. Lower it for a gentle API, raise it for a big fleet.

How a run reaches a provider
  • The portal runs terraform from wherever the portal runs — in a cluster, that is the pod's own network. A provider endpoint it cannot reach is a run that fails however correct the .tf is.
  • Each stack keeps its own working directory under the data volume, so terraform.tfstate and the downloaded providers persist between runs — Terraform's memory of what it built.
  • The provider credential is encrypted at rest and injected as environment variables at run time; it is never written to disk and never shown back on the stack page.
  • Every run keeps the whole output, the exact command, who started it and Terraform's own change summary.
