{{- if and .Values.ingress.enabled (not .Values.portal.cookieSecure) }}

{{- if gt (int .Values.replicaCount) 1 }}
NOTE: replicaCount is {{ .Values.replicaCount }}. Replicas stay coherent (a
shared revision row invalidates every process's cache on write), and the chart
pins them to one node so they can share the volume — SQLite is not safe over a
network filesystem. This scales capacity, not node-failure survival.
{{- end }}

What it is: {{ .Values.service.port }}/tcp, one volume at {{ .Values.persistence.mountPath }},
running as uid {{ .Values.podSecurityContext.runAsUser }} with a read-only root
filesystem. It needs no cluster permissions of its own — it reads other clusters
with kubeconfigs you paste into it.

{{- if and .Values.persistence.enabled (not .Values.persistence.storageClass) }}

CHECK YOUR DEFAULT STORAGE CLASS. The portal keeps its database in this volume,
and SQLite's write-ahead log is not safe on a network filesystem — NFS locking
is advisory, and a lost lock is a corrupted database rather than a slow one. If
your default class is NFS-backed (nfs-client, nfs-subdir-provisioner, an EFS or
Azure Files class), set a local one instead:

  --set persistence.storageClass=<a local-path or hostpath class>

Object storage and network volumes are fine for the Ollama model cache
(ollama.persistence.storageClass) — those files are read-only once written.
{{- end }}
